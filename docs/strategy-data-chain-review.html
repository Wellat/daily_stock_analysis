架构/功能审阅
基于当前工作区

策略数据同步 → 决策 → 回测/实盘 → 订单链路审阅报告

审阅范围：可转债一期统一策略架构、现有 Strategy Lab、Live Strategy、QMT 订单链路、RuntimeScheduler、数据同步页面及 Web API。结论不是“代码能编译”式检查，而是对真实运行闭环、失败边界、数据一致性和可观测性的审计。

总体结论：当前实现已具备若干可复用基础组件，但尚未达到可安全运行的端到端闭环。存在 4 项高风险阻断、9 项中风险缺口 和若干清理/一致性问题。当前不建议直接开启自动实盘。

一、目标链路与当前实现

Provider / StrategyLabDataSyncService→StrategyLabSyncRun→MarketContext→StrategyBase.evaluate→StrategyDecision→ExecutionPlanner→TradingOrder→QMT pending/callback

已存在并可复用

  • StrategyLabDataSyncService 已有 provider 拉取、分阶段 upsert、运行状态和取消机制。
  • RuntimeSchedulerService 支持后台任务、按日期防重复和异常隔离。
  • TradingOrderService 与 QMT pending/callback API 已形成基本执行链路。
  • 新策略包提供 MarketContext、StrategyDecision、low-premium 和执行器骨架。

当前新增但未完全接通

  • 策略决策表与订单 decision_id 已定义，但决策记录没有完整 API/生命周期管理。
  • 14:20/20:00 scheduler 任务已注册，但盘中结果没有成为实盘下单的强制门禁。
  • 回测执行器是独立适配器，尚未接入 StrategyLabService/Engine 的真实回测路径。

二、严重问题（必须先修）

等级问题与证据影响修复要求
高盘中同步没有门禁。scheduler 的 cb_intraday_sync 只调用同步；LiveStrategyService.run() 不查询当日 intraday 的 StrategyLabSyncRun，14:30 任务仍可直接决策和建单。14:20 网络失败、数据过期或只完成部分阶段时仍可能生成实盘订单，违反 fail-closed 目标。新增唯一的“可用快照”查询服务；run/preview 均先校验状态、关键阶段、快照年龄。正式 run 不通过则绝不创建订单；preview 仅返回阻断诊断。
高所谓盘后增量尚未实现。run_scheduled_sync() 最终调用 sync_provider_convertible_bonds()，provider 仍按现有契约拉取全量数据；没有按各表最新成功日期计算缺口。运行时间、上游压力和重复写入不可控；“一期严格增量”的产品承诺与实际行为不一致。为 basic/terms/factor/event 分别计算水位；provider 支持日期范围/标的范围；只补缺口并保持幂等。没有日期范围能力时必须明确记录为全量而非伪称增量。
高风控恒通过。LiveStrategyService.run() 落库时硬编码 risk_status="passed"、risk_json={"passed": True}，从未调用 ExecutionPlanner 的 cash 检查或任何真实风控；data_sync_before_run 配置项保存后从未被读取。“风控通过”是假象，实盘可能在资金不足、数据未同步的情况下直接建单；配置承诺了“先同步再决策”但未实现，属契约漂移。run 前真正执行风控（cash/持仓/事件），把真实结果写入 risk_status/risk_json；实现 data_sync_before_run 语义，未同步或风控不通过则 fail-closed 不下单。
高event_check 模式下 target 被无条件覆盖。run() 中 if mode == "event_check": target = {} 之后，紧接着的 target = {d.symbol: ... for d in decisions if d.action == "buy"} 无条件重写，导致 event_check 仍会填充 buy 目标，与“event_check 只做卖出”语义矛盾。event_check 可能产生错误的买入目标/订单，直接威胁实盘正确性。按 mode 分支隔离 target 计算：event_check 只产出 exit 决策与卖出 rebalance，不生成 buy target；补 event_check 模式回归测试。

三、中风险功能缺口

领域发现建议
同步状态模型增加了 run_kind/data_snapshot_at/quality_status/notification_status，但完成/失败流程没有统一写入这些字段；现有查询 payload 也没有展示。将状态更新集中在编排器，增加阶段状态 JSON、质量诊断和通知结果 API。
通知邮件在 run_scheduled_sync 外层发送，手工/异步 provider sync 路径不会统一通知；通知结果也未持久化。统一编排器负责 success/failure 通知，并写回 notification_status；避免重复发送。
调度时间匹配依赖 30 秒轮询的精确 HH:MM 字符串；进程重启、时钟漂移或任务执行跨分钟时可能漏触发。未见交易日判断。用“目标时间窗口 + 运行记录幂等”替代精确字符串；统一复用 trading-day 检查。
回测BacktestExecutor/ExecutionPlanner 未接入旧 StrategyLabEngine。low-premium 新类只服务 LiveStrategy，无法证明回测与实盘同一上下文得到一致组合。增加兼容 adapter，在 StrategyLabService 的单日循环中调用新策略；补充同上下文双执行器一致性测试。
事件检查策略层支持 event_check，但同步上下文只把 event_blocked 压成通用事件，强赎/下修/回售的事件类型和详情未完整注入。从 StrategyLabCbEvent 映射完整事件类型、日期和详情，并覆盖无可用持仓只记风险不下单。
配置兼容新增 Config 字段已解析，但 Web 实盘面板未完整展示同步门禁、数据年龄和同步状态；保存配置字段与 UI 仍不完全对称。增加状态卡、阻断原因、最后成功快照；保存/读取字段双向测试。
数据库迁移SQLite 已补 trading_orders.decision_id 等列，但新同步字段、strategy_decisions 表在既有生产库上的迁移/索引/外键完整性没有独立迁移版本。增加显式 schema migration 版本和 upgrade 测试，检查旧库、空库、重复启动三种场景。
配置硬编码LiveStrategyService 中 LIVE_ACCOUNTS = {"testS", "135129739"} 写死在代码里，违反仓库“不写死账号”的硬规则。将允许的实盘账号改为配置项（如环境变量/Config 字段），并保留默认空或显式白名单校验。
幂等竞态run() 先查 existing 再创建 LiveStrategyRun，但“查”与“建”不在同一事务/锁内，并发调用可能产生重复 run 与重复订单。用唯一约束（config_id + trade_date + mode）或事务内加锁，把 check-then-act 收敛为原子操作。

四、订单与前后端闭环审阅

已闭环部分

  • Web 可调用 /api/v1/trading/orders，订单列表字段与 QMT 状态字段基本对应。
  • 实盘运行创建 LiveStrategyRun、LiveRebalanceBatch 和 TradingOrder，订单可通过 run/batch 查询。
  • QMT 拉取 pending、回调 submitted/filled/rejected 的旧链路未被策略架构直接破坏。

尚未闭环部分

  • Web 实盘工作台没有“盘中数据可用/不可用”强门禁展示，也没有 event_check/rebalance 的清晰运行切换。
  • 策略决策列表 API 仅提供 live run 下的查询；回测成交与决策没有 decision_id 关联。
  • 交易记录页面没有显示决策 UID、运行 UID、批次 UID、失败原因等审计字段的完整契约。
  • 订单幂等键 client_order_key 只在规划器内生成，当前 TradingOrder 表/服务没有持久化或唯一约束，重复运行保护仍主要依赖 run 记录。

五、重复造轮子与应清理项

  • 旧 engine.list_builtin_strategies() 保留一整份 legacy 元数据，新 registry 又生成一份；应让 registry 成为唯一元数据源，通过兼容转换保留旧字段。
  • LiveStrategyService 内仍手工构造 MarketContext，和新建的 StrategyContextService 重复；应删除手工映射，统一由 context service 负责。
  • LiveExecutor 已存在，但 LiveStrategyService 仍直接循环调用 TradingOrderService.create_order()；应二选一，避免两条执行语义漂移。
  • run_scheduled_sync() 目前只是 provider sync 的薄包装，尚不是真正的 orchestrator；应避免以“scheduled”命名掩盖未实现的阶段质量、增量和门禁逻辑。
  • 策略代码存在大量压缩式单行语句，降低审计可读性；实盘风控路径应改为清晰分支并补结构化日志。

六、建议的落地顺序

  1. 先修安全阻断：实现盘中同步可用性查询和 run 前 fail-closed 门禁；补“失败/过期/阶段不全绝不下单”测试；同时修复“风控恒通过”（真实执行风控并落库）与 event_check 模式下 target 被覆盖的 bug。
  2. 收敛同步编排：统一创建/完成/失败/通知状态，真实实现严格缺口增量；为旧 SQLite 增加显式迁移版本。
  3. 收敛执行层：LiveStrategyService 使用 ExecutionPlanner + LiveExecutor；StrategyLabService 使用同一策略与 BacktestExecutor。
  4. 完善事件与审计：注入完整事件详情，持久化 decision UID/client key，并补决策→成交→订单查询。
  5. 完成 UI 闭环：同步状态卡、快照年龄、门禁原因、模式区分、决策详情和订单审计字段；再考虑自动启用实盘。

八、最终判断

功能完整性：基础骨架约 40%–50% 完成，旧链路可用，新链路尚未形成可证明的一致闭环。

严重 bug：盘中同步失败仍可能下单是最高优先级问题；“增量同步”当前名不副实是第二个高风险问题；此外“风控恒通过”（risk_status 硬编码 passed）与 event_check 模式下 target 被无条件覆盖，均会直接威胁实盘正确性，需一并修复。

上线建议：保持自动实盘关闭。先完成门禁、真实增量、迁移、统一执行器和回归测试，再进行小账户/模拟账户灰度。

回滚策略：保留旧 StrategyLab/TradingOrder 路径；新策略运行通过配置关闭。数据库字段采用向前兼容 nullable/default 迁移，必要时停止新 scheduler 任务即可回退到旧同步入口。
